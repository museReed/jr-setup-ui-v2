# Task Card PRD 怎麼寫

目標只有一句：**讓 v2 的行為與驗證標準跟舊版完全一致**。

所以每份 PRD 不是「這張卡應該做什麼」的設計文件，而是**從舊版反向抽出來的規格**。差別很大：
前者會讓寫的人（或 AI）用「合理設計」填空，而合理設計正好就是我們踩過的每一個退步。

## 為什麼要這樣寫（四個實際發生的退步）

| v2 做了什麼 | 舊版做什麼 | 為什麼會發生 |
|---|---|---|
| `npm install -g` 裝 CLI | 官方原生安裝器 | 沒去看 `installers.js`，那裡有 EACCES 的實測記錄 |
| hook 驗證改成「跑腳本讀 exit code」 | 開真的 claude 看攔截訊息 | 換了做法，沒發現**命題**也跟著換了 |
| 全螢幕三格兩步壓成一格人眼勾選 | 三格兩步，第三格程式比對 | 整格消失，沒有清單擋住 |
| stdin 少一個 `\n` | `${text}\n` + 等 callback | 沒有逐字對照 |

共同點：**不是想不到，是沒去看**。而舊版的正本不在 code 的形狀裡，在**註解**裡——`pipefail`
為什麼不能省、為什麼 `where` 不是 `true`、為什麼驗證題的提示詞不能寫出串接指令的字面，全都
是註解在講。把 code 讀一遍看懂它在做什麼，仍然會漏掉這些。

還有一類更隱蔽的：**做了半套**。擋掉 claude 自動開瀏覽器（對），但沒做配套的連結入口（斷路）；
加了輸入框（對），但沒送換行（斷路）。半套比不做更糟——不做至少學生知道要自己來。

## 三條硬規則

1. **每一條都要指得回舊版出處**（檔案 + 行號，或 `CASES` 的 case 名稱）。沒有出處的條目標成
   「新增」並自己寫理由——這樣「哪些是繼承、哪些是我們新想的」一眼分得出來，而「新增」的
   部分是唯一沒有實測背書的，要另外盯。
2. **命題與做法分兩層。** 命題＝這一格要證明什麼為真；做法＝怎麼證明。命題不可改；做法預設
   照舊版，要換必須寫下**新做法排除得了哪些失敗、排除不了哪些**。
3. **每一格標「誰判定」**（結構探測 / 行為驗證 / 副產物比對 / 人眼勾選）。可判定的東西降級成
   人眼勾選是退步，這個欄位讓它藏不住。

## 骨架

`§1 §2 §3` 必填，其餘有才寫（`§2` 一行也算數）。

```
1. 命題          這張卡做完之後，什麼事變成真的（1-3 句）
2. 舊版出處      對應舊版哪些檔案/行號/case 名稱 ← parity 的錨
3. 逐格清單      格 id · 標題 · 細節 · 誰判定 · 判定來源 · 這個判定證明不了什麼
4. 步驟與按鈕    每顆按鈕跑什麼、綁在哪一格（stepId）
5. 動作規格      指令、平台差異、環境變數，每項附舊版證據
6. 驗證題全文    提示詞逐字 + 要找的關鍵字 + 逾時；標「哪幾個字不能改，為什麼」
7. 失敗長相      每種失敗 → 學生看到什麼 → 我們給什麼線索
8. 已知怪癖      ANSI 色碼、輸出折行、非零 exit 是良性、包裝函式吃旗標…
9. 副作用成本    會不會開視窗 / 花 token / 需要登入 / 需要網路
10. Non-Goals    被否決的做法 + 證據 + 什麼條件下可以重開
11. 驗收         可執行指令 + 真機觀察點
```

### §7 的判準

每一條動作都要回答：失敗時學生看到什麼？**如果答案是「沒有反應」，這條規格就還沒寫完。**
今天兩個 bug 的症狀都是「什麼都沒發生」（吞掉 409、少了換行）。

### §11 的判準

**驗收不能只有「UI 綠燈」。** `--permission-mode` 被 shell 包裝函式吃掉那次，UI 一切正常，只有
去看行程參數才發現旗標不見了。§11 分兩欄：可執行指令 ／ 真機觀察點（看行程參數、看事件流、
看寫出去的檔案內容）。

真機那一欄寫完之後，對照 `docs/standards/vm-checklist.md` 補上那張卡會踩到的共通項——那份是
歷次 VM 驗收的沉澱，每一條都寫了「壞掉時長什麼樣」。

## 不另外寫 TDD 設計文件

這個產品最重要的那幾件事，單元測試本質上證明不了——安裝器裝到哪、Claude Code 有沒有真的
載入 hook、旗標有沒有被包裝函式吃掉，都只有真機證明得了。所以這裡的品質指標不是覆蓋率，
是**每一條實測結論有沒有被鎖住**。

測試分三層，長在 PRD 既有的節裡：

| 層 | 是什麼 | 從哪來 | 什麼時候寫 |
|---|---|---|---|
| 守衛測試 | 防止**整類**錯誤重演：孤兒代號、分層、常數單一來源、卡片涵蓋率 | 架構層級 | 一次寫好，之後保護所有新卡 |
| 迴歸鎖 | 每修一個 bug 補一題，測試名稱就是那句實測結論 | §7 失敗長相 | 跟實作同一次交付 |
| 真機驗收 | VM 檢查表 | §11 真機觀察點 | 每張卡做完 |

不強制 red-first：對這種以整合與 UI 為主的產品，先寫紅燈的成本高（要 mock 環境、DOM、子行程）
而發現力低。要求的是**測試與實作同一次交付**，且測試名稱寫成一句完整的斷言。

## 派 codex 實作時

一張 PRD 對應一次 codex 實作。spec 的驗收條件直接從 §11 抄過去，並且：

- **spec 必須指名對應的舊版檔案讓它先讀**（Reed 定的原則：舊版那套是跑成功過的）
- **驗收條件要鎖住「這次改動」的範圍，不是環境的絕對狀態**。寫 `grep "catalog"` 完全無輸出，
  會掃到註解裡的歷史說明；寫 `git status` 完全空白，會掃到別人留下的 worktree。兩次都害
  codex 正確地停手回報矛盾
- 守衛測試要**反向驗一次**：故意加一行違規，確認它真的會紅。綠燈也可能是因為它什麼都沒測
